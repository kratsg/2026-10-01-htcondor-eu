One slide of framing, then it's all implementation. The way I think about an agent is three blocks. The model, which you can swap: frontier API or open weights you host yourself. The harness, Claude Code, Codex, Copilot, also swappable. And the third block, the facility's context and tools: where the data lives, how you submit jobs, who you are. That third block is the only durable, tractable piece, and it's the one we, the people running the facility, control. Furnishing context is an infrastructure problem, not a prompt problem, which is why I think it belongs in this room. The model and the harness change week to week, and that's fine; they're not what holds us back. A concrete example, same prompt to both. Ask a generic model where your batch job's outputs should go and it'll say next to the job, your home area, and the big files blow your quota in minutes. A model that knows the facility sends big outputs to fast local scratch and keeps small summaries in the backed-up home. The model didn't get smarter; we gave it context. And the flip side: without context it should stay quiet. Ours once confidently recommended tuning for the wrong filesystem, so our rule is ungrounded means silent.

One minute of level-setting. The Model Context Protocol is an open protocol, originally from Anthropic, now with a public spec and SDKs everywhere. The assistant, whatever it is, Claude, Gemini CLI, an editor, speaks MCP to a server someone writes. That server can run on your laptop or be hosted at a facility, and it talks to what we already have: rucio for datasets, AMI for metadata, HTCondor for batch. For this room: it's a standard way to put a facility service in front of any model, the same way you'd put an API in front of a schedd. Tools are the primitive that matters in practice: typed functions the model can call, described by a name, a schema, and a docstring. Not prompt engineering, not a custom model: ordinary interface design for an unusual caller.

Backup, for the "how do I start" question. This is the barebones structure rucio-mcp started from: FastMCP, the native Rucio client, one decorated function. The decorator turns the signature into the JSON schema and the docstring into the description. Point at the left and the right together: the name, the two typed parameters, and that docstring are literally everything the LLM knows about this tool, which is why the docstring is API surface. Two pieces of advice if you do this tomorrow: wrap the client library, not the command-line tool, because you want structured data on your side of the boundary; and start with stdio on your laptop, where credentials come from your environment like they do for any script. Overview · the platform boundary

A credential-brokered MCP gateway

One endpoint in front of the facility’s services. The LLM client never holds raw credentials; the broker authenticates the user, mints per-service credentials, and audits every tool call.

Identity, authZ, credential brokering, and audit in one place: the same boundary a facility wants in front of its services, with or without AI.

rucio-mcp · ami-mcp · atlasopenmagic · panda-mcp · condor-mcp (Bockelman, CHEP 2026).
The same thing as one architecture picture, if you want the overview. The client, Claude, Gemini, whatever, holds only a bearer token. It hits the front door, mcp.af.uchicago.edu, which is oauth2-proxy in front of the AF's Keycloak. Behind that, the FastMCP aggregator and the credential broker do identity, authorization, credential brokering and audit, and fan out to the MCP servers. The broker is the only thing that ever touches raw x509 or IAM material. Adding the Nth backend is no code change. It's deployed with Flux and Helm. The point for this room: that boundary is the one you'd want in front of your services anyway, AI or not.

The first design choice

One MCP, many, or a gateway?

One server, many sites

one deploy   per-VO auth in one process

One server per site

clean isolation   N servers to run

Single gateway

one identity   token sprawl / choke point

We run the gateway: one identity, one place to authorize and audit. Next: how we handle token sprawl and the choke point.

FastMCP composition = one auth provider per server; that constraint drives a lot of the design.

Once you have more than one MCP server, the first real decision is topology. One server that knows about every experiment is one deploy, but now per-VO auth lives in a single process. One server per site is clean isolation, and N things to run and patch. Or a single gateway in front of many sub-MCPs: users see one endpoint and one identity, and you get one place to authorize and audit every call. We went with the gateway. It has two costs you can see on the card: token sprawl, because every backend needs its own credential, and a choke point, because everything goes through it. The next few slides are how we handle those two. One practical constraint pushed us there: FastMCP composition gives you one auth provider per server, so you can't just mount ten servers with ten different auth stories into one process.

The thing to notice is how many different tokens exist: the personal access token the client holds, the ten-minute JWT the broker mints for exactly one backend, and the VOMS proxy the backend redeems directly from the broker's vault. Each hop exchanges rather than forwards, which is what the MCP spec's authorization section requires. Also notice what the broker's JWT does not contain: permissions. It says who you are; what you may do is decided at the gateway from your Keycloak groups, on every call, so removing someone from a group takes effect immediately instead of when their token expires.

  • One rule, different ways to implement, e.g.: k8s owner labels · kernel uid/gid · the VOMS nickname in your proxy
  • Who you are comes from the identity provider (e.g. Keycloak) on every call, not from what a token claims

The principle

Do not expose dangerous parameters; derive them from verified identity.

af-jupyterlab-mcp tools/jupyterlab.py, abridged.
Every agent-facing schema in the fleet has the same absence: there is no owner or username parameter anywhere. The user is whoever the verified token says, full stop. An LLM argument can be hallucinated or injected; a verified claim can't. One rule, implemented differently per backend: Kubernetes owner labels for notebooks, an actual setuid subprocess for the filesystem so the kernel does the enforcement, and the VOMS nickname inside your redeemed grid proxy for Rucio and AMI. And one sharpening: even the token doesn't carry authority. Who you are, your groups and your unix identity, is looked up from the identity provider, Keycloak in my case, on every call, rather than trusted from token contents. That's what makes removing someone from a group take effect in seconds instead of whenever their token expires.

Keep credentials out of the MCP

Lifetime == one call

e.g. a VOMS proxy or Kerberos ticket: fetch it → 0600 temp file → one backend call → delete it. The MCP server keeps nothing.

Exchange, never forward

The user's token never goes downstream (the spec forbids it). Each hop gets a fresh short-lived JWT, valid for one service, expiring in 10 minutes.

One service per secret

e.g. only condor-token-service touches the Condor pool key; the broker is its only allowed caller, and it returns short-lived IDTokens.

bad: a token service deciding permissions

if "atlas-users" in token["groups"]:
    mint_ticket(user)
# a second copy of the access rules,
# trusting whatever the token claims

good: it only verifies who is calling

claims = verify(token, aud="krb5-token-service")
mint_ticket(claims["sub"])
# the gateway already decided permissions;
# this token proves who, from the broker

sketch; written into all three token services' docstrings (krb5 app.py)

Never store secrets in the MCP server. Keep them in a vault (OpenBao, here) behind the broker, and mint short-lived credentials per call.

The architectural heart, and the abstract's promise: authentication without exposing user credentials. Three moves across the cards. First, credential lifetime equals tool-call lifetime: when rucio-mcp needs your grid proxy, it fetches it, writes a mode-0600 temp file, makes exactly one backend call, and deletes it, success or failure. I test the deletion. Second, exchange instead of forwarding: the user's own token never goes downstream, which the MCP spec explicitly forbids. What goes downstream is a fresh JWT the broker mints, valid for exactly one service and expiring in ten minutes. Heavy material like proxy files never passes through the gateway at all; the backend fetches it directly from the broker. The bad-versus-good pair is about where permission decisions live. Bad: the token service checks the token's groups itself. Now the access rules exist in two places, and this copy trusts whatever the token happens to claim, so a stale token keeps its access. Good: the service verifies only that this is a valid broker token addressed to it, and mints for whoever the token says. The permission check already happened once, at the gateway, against live Keycloak groups. That rule is written into all three token services' docstrings so nobody re-grows a second permission layer. And nothing secret lives in an MCP server: it's all in a vault, OpenBao in my case, behind the broker. Deep-dive below on the three custodians, including the HTCondor one.

The custodians · deep-dive

voms-token-service

The only pod that sees home dirs and Globus passphrases. Runs voms-proxy-init impersonated; privilege floor found live, five times.

krb5-token-service

Password → kinit → ticket; zero secrets at rest, passwords zeroed on every exit path. Rate limiter protects CERN's lockout counter, not itself.

condor-token-service

Runs condor_token_create next to the pool key, which "must never reach the broker": it can mint any identity.

Why three services, not one

Different privilege floors (root+caps / none / one init container). Merging them forces the union of privileges onto everything. Each is a one-question audit: "did this call come from the broker?"

Orchestrate the hardened native binary; parse artifacts (ccache bytes, PEM), never CLI prose.
Deep-dive for questions. Three services because three root secrets with three different privilege needs. voms needs root plus capabilities to read user keys, and every one of those facts was discovered in production: grid tooling checks file ownership, not just mode. krb5 needs no privileges at all and holds nothing; its rate limiter exists to protect CERN's account-lockout counter, a third party, which is my favorite example of consequence-driven design. condor sits next to the symmetric pool key that can mint tokens for any identity, which is exactly why it must never reach the broker's trust domain. Common thread: all three shell out to the battle-tested native binary and parse artifacts, ccache bytes and PEM, never the human-readable CLI output, which turned out to be locale-dependent.

Lessons learned · ↓ four more

What breaks at ten MCPs (that one never sees)

Design decisions baked into the AF MCP Platform

  • Name collisions: two MCPs serve a tool with the same name; fix = a prefix per service (rucio-atlas_*, fs_*)
  • Each service gets its own fixed OAuth audience, pinned in config, never derived from a name that can change
  • Listing needs credentials too: some MCPs require auth even for tools/list, so the gateway mints one just to enumerate
  • New tools are opt-in: when an MCP releases a tool, it stays disabled until an operator maps it at the broker
  • Authorization is plain RBAC: Keycloak group → permission → tool
  • A dead backend disappears from tools/list instead of every call failing

Adding the Nth MCP

Each MCP is added via config (Infrastructure‑as‑Config: Helm charts on Kubernetes). Sometimes it needs a token service, sometimes a bridge, never changes to the MCP itself.

af-mcp-platform issues #113, #257, #121 · 289 commits, 77 days, 1,337 tests. ↓ more scars
Everything so far was about one server at a time. At ten, a different class of problem appears, and none of it is in the MCP spec. Quick tour: name collisions, because two backends will eventually serve a tool with the same name and the failure is silent, so every service gets a prefix. OAuth audiences: each service's audience is pinned in config; I learned the hard way not to derive it from a display name, because a rename broke authentication for everything at once. Listing: some MCPs need auth just to enumerate their tools, so the gateway mints a credential for the listing itself. New tools are opt-in: when a backend ships a new tool, it stays disabled until an operator maps it to a permission at the broker. Authorization itself is nothing exotic, plain RBAC from Keycloak groups. And when a backend dies, its tools leave the list rather than erroring one call at a time. The payoff: adding the Nth MCP is configuration, infrastructure-as-code. Sometimes it needs a token service, sometimes a bridge, but you never modify the MCP itself.

This is the first lesson chronologically, shown as bad versus good. ami-mcp wraps a twenty-year-old metadata service. The naive wrapper worked and passed its mocked tests, and the output was unusable: a hundred raw fields per dataset, cross-sections in nanobarn with no hint, duplicate rows, multiplied by every dataset in the answer. The fix commit is literally titled "optimize MCP tools for LLM usefulness": pick the fifteen fields an analyst would pick, convert units visibly so the model can't silently mix nb and pb, deduplicate, and end every result with named follow-up tools so the model knows where to go next. And the callout: the docstrings keep getting fixed against the tools' real behavior. AMI is the one server where I teach the model a query language, so the documentation is executable; when a documented example was wrong, the model reproduced the wrong syntax verbatim, and I fixed the docs the way you fix code, against the live service.

Empty results carry the same routing hints. The error categories also feed my monitoring, so I can see which tools confuse the agent.

MCP results have an isError flag so clients can tell failure from success. I didn't set it at first; do both.

The classifier behind the right panel: rucio-mcp tools/_helpers.py (classify_error).
The consumer of an MCP is probabilistic: it course-corrects from what it reads, so an error message is not diagnostics, it's the next instruction. Left panel: the default, a raw exception. Best case the agent guesses; worst case it retries the same call. Right panel: what rucio-mcp returns for the same failure. The error comes back to the agent as a normal result rather than being raised into the server logs, and the recovery line names the exact next tool, so most failures heal themselves inside the loop. Empty results, which are the most common silent failure, get the same treatment. Two housekeeping notes: the same error categories feed my monitoring, so I can literally chart which tools confuse the agent; and MCP has a flag on results, isError, that lets clients and gateways distinguish failure from success. I skipped it at first and my audit log counted failing calls as successes for a while. Return the friendly prose AND set the flag.

And cap the server's work too: rucio-mcp once fetched that whole 500k-file container upstream just to serve one 50-row page. Paginate the upstream iterator, not just the output.

The real footer text and iterator fix: rucio-mcp tools/_helpers.py (paginate_iter).
Same bad-versus-good format. Left: what a naive file-listing tool does with a big container: half a million lines into the LLM's context window, which destroys the conversation, and the server fetched all of it from Rucio to boot. Right: what rucio-mcp actually returns. A hard limit of fifty, enforced server side, and the two lines at the bottom matter most: the output says it truncated and says exactly how to get the next page. Truncation the LLM can't see silently distorts what it believes; truncation it can see is just the next tool call. The callout is the second half of the lesson, and I learned it the embarrassing way: for a while the output was perfectly paginated while the server still downloaded the entire container upstream to serve each page. An external contributor caught it. Cap what the backend does, not just what the LLM reads. Same principle at the gateway: it writes its own short instructions instead of forwarding every server's, and only lists the tools you're allowed to call.

Three more things that land on the facility once agents are users, each with a deep-dive I gave at Nikhef, linked here rather than repeated. Client identity: with CIMD the client_id is an HTTPS URL to a metadata document the client hosts, and the server fetches it. No registration endpoint to abuse and no database of client ids to garbage-collect, which is why the platform moved off dynamic registration; the MCP spec has since deprecated DCR in favor of it. The cost is that the server makes outbound fetches, so you block private IPs and cap size and time. Shell access: ssh-oidc from KIT and EOSC-synergy replaces the permanent private key with a short-lived, revocable federated credential. Anything with your ssh-agent socket, including a coding agent, can sign as you forever; with this, the blast radius is minutes. Sandboxing: pods by default on Kubernetes, bubblewrap or similar on bare login nodes, eBPF class policy for fine-grained file and syscall rules, and privilege that's earned and human gated. The honest gap: today a harness can advise but can't reliably hard-deny a command at the user level. Real blocking needs a policy engine on the node.

Interfaces that travel

Across LLM providers

  • Design for the least-capable LLM client: e.g. Claude Desktop had no OAuth discovery, so I added personal access tokens; gemini-cli choked on an OAuth metadata fallback, so I deleted it
  • Standard OAuth, standard transports, no provider-specific hooks

Across experiments

  • rucio-mcp already serves ATLAS, CMS, DUNE, ESCAPE: the domain layer is VO-agnostic
  • Transplant the shape (broker + custodians + config-only services), not the CERN-specific code

Interoperable tool interfaces are likely to matter more than LLM-specific integrations.

↓ how my choices scored against the evolving MCP spec
The abstract's closing claim, made concrete. Across providers: the discipline is designing for the least-capable client. I had a genuinely cleaner design for routing based on OAuth scopes, fully written up, and I shelved it because only one client on the market supports the feature; the write-up is committed next to the code. Same story with the OAuth metadata fallback I deleted after a different client choked on it. Standard auth, standard transports, nothing provider-specific: that's what "works across providers" costs. Across experiments: rucio-mcp is already multi-VO because Rucio is, and the whole facility shape, broker, custodians, config-only services, transplants to any lab. What doesn't transplant is the CERN-specific plumbing, and that's fine: it's all behind one provider interface and per-service config. If you take one sentence home, take the abstract's: interoperable tool interfaces will matter more than model-specific integrations.

Backup scorecard, for the "is MCP stable enough to build on" question. Three of my production-driven choices were later standardized in the 2.0 spec: statelessness, client-id metadata documents, and betting on tools as the durable primitive. The auth model is compliant with the spec's strictest MUSTs, including the token-passthrough prohibition, which the broker architecture essentially exists to satisfy. At PyHEP.dev a few weeks ago the last two rows were misses: markdown only, no output schemas and no tool annotations. Both are fixed now. Tools carry read-only and destructive annotations, so the gateway no longer keeps its own list of which tools write, and the tools that return data have output schemas. If you start tomorrow, start with both.

When is an MCP server appropriate?

Build one when

  • a library or service scientists already use
  • assistants need it repeatedly, across clients
  • you want to control what context the agent gets injected with
  • you can bound outputs and make errors recoverable

Skip it when

  • a one-off script would do
  • the backend's API is still churning under you
  • the "tool" would hand the LLM a credential
From “Model Context Protocol for Scientific Software”, PyHEP.dev 2026 · the full checklist
If you're thinking about putting something of yours behind MCP, here's my rule of thumb. Build one when there's an existing library or service with real users, when assistants will need it more than once and from more than one client, and when you can actually bound the outputs and make the errors recoverable, because those are the two things the model experiences directly. Skip it when a script would do, when the backend has no stable contract to wrap, or when the honest implementation would hand the model a credential; fix that boundary first.

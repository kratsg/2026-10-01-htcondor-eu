Hi, I'm Giordon, I build analysis-facility infrastructure at UChicago for ATLAS. Three slides, big picture. The way I think about an agent is three blocks. The model, which you can swap: frontier API or open weights you host yourself. The harness, Claude Code, Codex, Copilot, also swappable. And the third block, the facility's context and tools: where the data lives, how you submit jobs, who you are. That third block is the only durable, tractable piece, and it's the one we control. This is the "just furnish context" point from the paper on the agenda, but in practice furnishing context is an infrastructure problem, not a prompt problem. A concrete example. Ask a generic model where your batch job's outputs should go and it'll say next to the job, your home area, and the big files blow your quota in minutes. A model that knows the facility sends big outputs to fast local scratch and keeps small summaries in the backed-up home. The model didn't get smarter; we gave it context. And the flip side: without context it should stay quiet. Ours once confidently recommended tuning for the wrong filesystem, so our rule is ungrounded means silent.

One minute of level-setting. The Model Context Protocol is an open protocol, originally from Anthropic, now with a public spec and SDKs everywhere. The assistant, whatever it is, Claude, Gemini CLI, an editor, speaks MCP to a server someone writes. That server can run on your laptop or be hosted at a facility, and it talks to what we already have: rucio for datasets, AMI for metadata, HTCondor for batch. In JFC terms, this is a standard way to plug in the "execution framework" and the context, so it works with any model. Tools are the primitive that matters in practice: typed functions the model can call, described by a name, a schema, and a docstring. Not prompt engineering, not a custom model: ordinary interface design for an unusual caller.

A facility-native MCP server must be…

Convenient

No extra barriers for analyzers*; self-service access to what the facility already offers.

Secure

Never leak your credentials to the agent; never leak sensitive experiment data**.

Auditable

Telemetry on usage: which tools get used, which don't.

*apart from having your own LLM assistant  ·  **depends on the experiment’s guidance

“Towards Agentic Analysis”, ATLAS AMG Weekly, 2026-09-04
So what does "behind the URL" need? Three requirements. Convenient: an analyzer shouldn't need anything beyond their own assistant, and access should be self-service to things the facility already provides. Secure: your credentials never reach the agent, and sensitive experiment data doesn't leak, where "sensitive" is whatever your experiment's guidance says. And auditable: we want telemetry on which tools actually get used, both for security and to know what to build.

This is the platform in one animated call: the portal landing page's own diagram, reproduced in the slide. Let it run one cycle while talking. Two authorized calls play through: the assistant asks, Auth, Policy, and Audit check green, the Broker mints a credential off to the side, the call lands on Rucio or HTCondor, and the answer comes back. The third cycle is the governance story in eight seconds: "Delete my /data datasets" passes Auth, fails Policy, the gateway buzzes red, and the assistant reports it is not authorized. Three things to say over it: credentials stay behind the broker, so the assistant never holds anything raw and the user's token is never forwarded downstream. Every call is authorized against group-based permissions, and the denials get audited too. And every credential is minted short-lived for exactly one service, used once, and deleted. And the design idea underneath, which I showed at Nikhef: the agent speaks intent, "get this dataset", "run this on the cluster", and the facility wires that to Rucio, HTCondor, whatever the backend is. Adding the next MCP server is configuration, never a change to the server.

Concretely, what's behind it today. Four MCP servers I wrote: rucio for dataset discovery and replicas, AMI for sample metadata and cross sections, a filesystem server that reads only your own files, and a JupyterLab server that manages your notebooks and runs code. Then the part nobody sees: identity brokering. You authenticate once against the facility's identity broker, and small token services mint a Kerberos ticket, a VOMS proxy, or an HTCondor token for you, short-lived, per call. And servers other people wrote plug in the same way: Brian Bockelman's HTCondor server, with Tadashi Maeno's PanDA and Jason Oliver's atlas-search integrations coming.

Secure the architecture, design the interface

Security is structural

  • No tool takes a username: identity comes from the verified token, never the LLM
  • No credentials in the MCP: vault → mint per call → use once → delete
  • Permissions decided once, at the gateway; new tools are opt-in

Treat the agent like a new student

  • Clear, narrow tasks: "find this dataset", not a raw API
  • A correct manual: it copies examples verbatim, so test them
  • Useful feedback: short answers; errors that say what to try next
Interoperable tool interfaces are likely to matter more than model-specific integrations.

Security, saved for the end as requested. The key idea: don't ask the model to be trustworthy, make the architecture not care. No tool in our fleet takes a username, so the schema literally can't express "read Bob's files"; who you are comes from the verified identity on every call. No MCP server holds a credential: the broker pulls from a vault, mints something short-lived for exactly one service, it's used once and deleted. And permissions are decided in exactly one place, the gateway, from plain group-based RBAC. A brand new tool stays off until an operator maps it. The other half is agent design, and the best mental model I have is a new grad student. Give it clear, narrow tasks shaped like how a physicist asks, "find this dataset", rather than a raw API dump. Give it a correct manual: the tool descriptions are what it reads, and ours once copied a broken example verbatim, so now we test every example against the live service. And give it useful feedback: keep answers short, since raw API rows swamped the model, and make every error say what to try next so it can recover on its own. Close: interoperable tool interfaces will matter more than model-specific integrations. Design the interface for the model, design the architecture for the credential.

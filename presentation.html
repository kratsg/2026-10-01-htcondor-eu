One slide of framing, then it's all implementation. The way I think about an agent is three blocks. The model, which you can swap: frontier API or open weights you host yourself. The harness, Claude Code, Codex, Copilot, also swappable. And the third block, the facility's context and tools: where the data lives, how you submit jobs, who you are. That third block is the only durable, tractable piece, and it's the one we, the people running the facility, control. Furnishing context is an infrastructure problem, not a prompt problem, which is why I think it belongs in this room. A concrete example. Ask a generic model where your batch job's outputs should go and it'll say next to the job, your home area, and the big files blow your quota in minutes. A model that knows the facility sends big outputs to fast local scratch and keeps small summaries in the backed-up home. The model didn't get smarter; we gave it context. And the flip side: without context it should stay quiet. Ours once confidently recommended tuning for the wrong filesystem, so our rule is ungrounded means silent.

One minute of level-setting. The Model Context Protocol is an open protocol, originally from Anthropic, now with a public spec and SDKs everywhere. The assistant, whatever it is, Claude, Gemini CLI, an editor, speaks MCP to a server someone writes. That server can run on your laptop or be hosted at a facility, and it talks to what we already have: rucio for datasets, AMI for metadata, HTCondor for batch. For this room: it's a standard way to put a facility service in front of any model, the same way you'd put an API in front of a schedd. Tools are the primitive that matters in practice: typed functions the model can call, described by a name, a schema, and a docstring. Not prompt engineering, not a custom model: ordinary interface design for an unusual caller.

So what does "behind the URL" need? Three requirements. Convenient: an analyzer shouldn't need anything beyond their own assistant, and access should be self-service to things the facility already provides. The point

The limiting factor is rarely the LLM. It's reliable, secure access to what scientists already use.

Start with the three-box diagram every MCP tutorial draws, because it's true: agent, server, backend, and the SDK makes that a weekend of work. Then reveal the second row: this is the same tool call as it actually runs in production. The user authenticated through Keycloak, the agent holds a personal access token, the gateway authenticates and authorizes once, a broker mints a short-lived identity token for exactly one backend, the backend redeems it for a real grid credential from a custodial service, and only then does Rucio hear about it. Every box in that second row exists because something broke without it. That's the talk in one line: design the interface for the model, design the architecture for the credential.

The first design choice

One MCP, many, or a gateway?

One server, many sites

One server per site

Single gateway

one identity   token sprawl / choke point

We run the gateway: one identity, one place to authorize and audit. The rest of the talk is paying down its costs.

FastMCP composition = one auth provider per server; that constraint drives a lot of the design.

Once you have more than one MCP server, the first real decision is topology. One server that knows about every experiment is one deploy, but now per-VO auth lives in a single process. One server per site is clean isolation, and N things to run and patch. Or a single gateway in front of many sub-MCPs: users see one endpoint and one identity, and you get one place to authorize and audit every call. We went with the gateway. It has two costs you can see on the card: token sprawl, because every backend needs its own credential, and a choke point, because everything goes through it. The rest of the talk is mostly how we pay those down. One practical constraint pushed us there: FastMCP composition gives you one auth provider per server, so you can't just mount ten servers with ten different auth stories into one process.

The deep-dive version of the animation, for questions. The thing to notice is how many different tokens exist: the personal access token the client holds, the ten-minute JWT the broker mints for exactly one backend, and the VOMS proxy the backend redeems directly from the broker's vault. Each hop exchanges rather than forwards, which is what the MCP spec's authorization section requires. Also notice what the broker's JWT does not contain: permissions. It says who you are; what you may do is decided at the gateway from your Keycloak groups, on every call, so removing someone from a group takes effect immediately instead of when their token expires.

The principle

Do not expose dangerous parameters; derive them from verified identity.

af-jupyterlab-mcp tools/jupyterlab.py, abridged.
Every agent-facing schema in the fleet has the same absence: there is no owner or username parameter anywhere. The user is whoever the verified token says, full stop. An LLM argument can be hallucinated or injected; a verified claim can't. One rule, implemented differently per backend: Kubernetes owner labels for notebooks, an actual setuid subprocess for the filesystem so the kernel does the enforcement, and the VOMS nickname inside your redeemed grid proxy for Rucio and AMI. And one sharpening: even the token doesn't carry authority. Who you are, your groups and your unix identity, is looked up from the identity provider, Keycloak in my case, on every call, rather than trusted from token contents. That's what makes removing someone from a group take effect in seconds instead of whenever their token expires.

Keep credentials out of the MCP

Lifetime == one call

e.g. a VOMS proxy or Kerberos ticket: fetch it → 0600 temp file → one backend call → delete it. The MCP server keeps nothing.

Exchange, never forward

The user's token never goes downstream (the spec forbids it). Each hop gets a fresh short-lived JWT, valid for one service, expiring in 10 minutes.

One service per secret

e.g. only condor-token-service touches the Condor pool key; the broker is its only allowed caller, and it returns short-lived IDTokens.

bad: a token service deciding permissions

if "atlas-users" in token["groups"]:
    mint_ticket(user)
# a second copy of the access rules,
# trusting whatever the token claims

good: it only verifies who is calling

claims = verify(token, aud="krb5-token-service")
mint_ticket(claims["sub"])
# the gateway already decided permissions;
# this token proves who, from the broker

sketch; written into all three token services' docstrings (krb5 app.py)

Never store secrets in the MCP server. Keep them in a vault (OpenBao, here) behind the broker, and mint short-lived credentials per call.

The architectural heart, and the abstract's promise: authentication without exposing user credentials. Three moves across the cards. First, credential lifetime equals tool-call lifetime: when rucio-mcp needs your grid proxy, it fetches it, writes a mode-0600 temp file, makes exactly one backend call, and deletes it, success or failure. I test the deletion. Second, exchange instead of forwarding: the user's own token never goes downstream, which the MCP spec explicitly forbids. What goes downstream is a fresh JWT the broker mints, valid for exactly one service and expiring in ten minutes. Heavy material like proxy files never passes through the gateway at all; the backend fetches it directly from the broker. The bad-versus-good pair is about where permission decisions live. Bad: the token service checks the token's groups itself. Now the access rules exist in two places, and this copy trusts whatever the token happens to claim, so a stale token keeps its access. Good: the service verifies only that this is a valid broker token addressed to it, and mints for whoever the token says. The permission check already happened once, at the gateway, against live Keycloak groups. That rule is written into all three token services' docstrings so nobody re-grows a second permission layer. And nothing secret lives in an MCP server: it's all in a vault, OpenBao in my case, behind the broker. Deep-dive below on the three custodians, including the HTCondor one.

The custodians · deep-dive

voms-token-service

The only pod that sees home dirs and Globus passphrases. Runs voms-proxy-init impersonated; privilege floor found live, five times.

krb5-token-service

Password → kinit → ticket; zero secrets at rest, passwords zeroed on every exit path. Rate limiter protects CERN's lockout counter, not itself.

condor-token-service

Runs condor_token_create next to the pool key, which "must never reach the broker": it can mint any identity.

Why three services, not one

Different privilege floors (root+caps / none / one init container). Merging them forces the union of privileges onto everything. Each is a one-question audit: "did this call come from the broker?"

Orchestrate the hardened native binary; parse artifacts (ccache bytes, PEM), never CLI prose.
Deep-dive for questions. Three services because three root secrets with three different privilege needs. voms needs root plus capabilities to read user keys, and every one of those facts was discovered in production: grid tooling checks file ownership, not just mode. krb5 needs no privileges at all and holds nothing; its rate limiter exists to protect CERN's account-lockout counter, a third party, which is my favorite example of consequence-driven design. condor sits next to the symmetric pool key that can mint tokens for any identity, which is exactly why it must never reach the broker's trust domain. Common thread: all three shell out to the battle-tested native binary and parse artifacts, ccache bytes and PEM, never the human-readable CLI output, which turned out to be locale-dependent.

What breaks at ten MCPs (that one never sees)

Design decisions baked into the AF MCP Platform

  • Name collisions: two MCPs serve a tool with the same name; fix = a prefix per service (rucio-atlas_*, fs_*)
  • Each service gets its own fixed OAuth audience, pinned in config, never derived from a name that can change
  • Listing needs credentials too: some MCPs require auth even for tools/list, so the gateway mints one just to enumerate
  • New tools are opt-in: when an MCP releases a tool, it stays disabled until an operator maps it at the broker
  • Authorization is plain RBAC: Keycloak group → permission → tool
  • A dead backend disappears from tools/list instead of every call failing

Adding the Nth MCP

Each MCP is added via config (Infrastructure-as-Code). Sometimes it needs a token service, sometimes a bridge, never changes to the MCP itself.

af-mcp-platform issues #113, #257, #121 · 289 commits, 77 days, 1,337 tests. ↓ more scars
Everything so far was about one server at a time. At ten, a different class of problem appears, and none of it is in the MCP spec. Quick tour: name collisions, because two backends will eventually serve a tool with the same name and the failure is silent, so every service gets a prefix. OAuth audiences: each service's audience is pinned in config; I learned the hard way not to derive it from a display name, because a rename broke authentication for everything at once. Listing: some MCPs need auth just to enumerate their tools, so the gateway mints a credential for the listing itself. New tools are opt-in: when a backend ships a new tool, it stays disabled until an operator maps it to a permission at the broker. Authorization itself is nothing exotic, plain RBAC from Keycloak groups. And when a backend dies, its tools leave the list rather than erroring one call at a time. The payoff: adding the Nth MCP is configuration, infrastructure-as-code. Sometimes it needs a token service, sometimes a bridge, but you never modify the MCP itself.

One slide for the operators in the room, because the same idea applies to us, not just to analysts. Think of it as levels of autonomy. Analyst-facing is low autonomy, high convenience. Operations is the middle, and this is running today: a scheduled agent scans HTCondor every morning and posts a Slack report, the state summary, a hold-reason breakdown, top users, jobs held more than seven days, and recommended actions. That morning it was 448 held out of about fourteen and a half thousand. When a user's jobs are stuck, it drafts an email with a specific fix. The real case here was an out-of-memory hold: raise request_memory based on the usage it actually observed against the limit, and write the big outputs to /data. A human replies "approve" in Slack, and only then does it send. Never autonomous. And honestly, there's no HTCondor MCP in this one, just skills around the condor CLI. Sysadmin-facing, the privileged lane, is where trust has to be earned and actions gated. The facility decides where the human gate sits at each level.

Interfaces that travel

Across LLM providers

  • Design for the least-capable LLM client: e.g. Claude Desktop had no OAuth discovery, so I added personal access tokens; gemini-cli choked on an OAuth metadata fallback, so I deleted it
  • Standard OAuth, standard transports, no provider-specific hooks

Across experiments

  • rucio-mcp already serves ATLAS, CMS, DUNE, ESCAPE: the domain layer is VO-agnostic
  • Transplant the shape (broker + custodians + config-only services), not the CERN-specific code

Interoperable tool interfaces are likely to matter more than LLM-specific integrations.

↓ how my choices scored against the evolving MCP spec
The abstract's closing claim, made concrete. Across providers: the discipline is designing for the least-capable client. I had a genuinely cleaner design for routing based on OAuth scopes, fully written up, and I shelved it because only one client on the market supports the feature; the write-up is committed next to the code. Same story with the OAuth metadata fallback I deleted after a different client choked on it. Standard auth, standard transports, nothing provider-specific: that's what "works across providers" costs. Across experiments: rucio-mcp is already multi-VO because Rucio is, and the whole facility shape, broker, custodians, config-only services, transplants to any lab. What doesn't transplant is the CERN-specific plumbing, and that's fine: it's all behind one provider interface and per-service config. If you take one sentence home, take the abstract's: interoperable tool interfaces will matter more than model-specific integrations.

Backup scorecard, useful for the "is MCP stable enough to build on" question. Three of my production-driven choices were later standardized: statelessness, client-id metadata documents, and betting on tools as the durable primitive. The auth model is compliant with the spec's strictest MUSTs, including the token-passthrough prohibition, which my broker architecture essentially exists to satisfy. The correction is authoring conventions and a retrofit. If you start tomorrow, start with structured outputs.
